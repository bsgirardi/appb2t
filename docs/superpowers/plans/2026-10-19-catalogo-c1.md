> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar descoberta e produto com visual avançado e configuração individual preservada até o contato consultivo.

**Architecture:** Estender o cadastro existente com definição comercial validada e revisão própria. Compartilhar validação/cálculo puro entre configurador e revisão no servidor, com projeção pública explícita e lista local v2 recuperável. Manter gestão comercial e recebimento de solicitações fora do C1.

## Global Constraints

- Até 20 linhas e 99 unidades por linha; até 8 campos, 20 opções por escolha, rótulo 60, ajuda 160, texto curto 1–120 e longo 1–500 caracteres.
- O que acompanha: 1.000 caracteres; condição de início do prazo: 240. Adicionais apenas por unidade, não negativos, duas casas e resultado monetário até 9999999999999999.99.
- Normalização NFC e trim externo; preservar espaços internos, acentos, maiúsculas e quebras. Contagem textual por pontos de código Unicode após normalização; não cortar emoji ao atingir limite.
- Lista/requisição: 256 KiB UTF-8; contato codificado acima de 6.000 caracteres usa cópia completa e canal sem corpo.
- Preço sob consulta nunca é zero fictício; frete separado; mensagem preparada não significa recebimento. Sem venda, reserva, pagamento, arquivos ou 3D.
- Poppins e tokens editáveis B2T, temas claro/escuro, 320/390/1440 px, ações públicas de 44 px, teclado e movimento reduzido.
- Não sobrescrever alterações administrativas. Testes mutáveis apenas em banco descartável comprovado; sem publicação ou migração operacional nesta execução.
- Ler AGENTS.md e os guias locais Next relevantes antes de código. Não instalar versões novas nem alterar lockfile por conveniência.

## Review Focus

1. Texto Unicode e nomes visualmente iguais: normalizar sem fundir personalizações distintas; testar em T1/T3.
2. Produto sob consulta atravessando a fronteira entre páginas: ordenar antes de paginar, sem expor preço interno; testar em T2.
3. V2 corrompido e aba antiga ainda aberta: não reimportar v1 sobre v2 nem perder dados; testar em T3.
4. Catálogo muda enquanto chega uma revisão: resposta antiga não libera contato nem desfaz edição recente; testar em T4/T6.
5. Foto removida na mesma gravação que altera opções: garantir vínculo válido ou limpar referência e recuperar galeria principal; testar em T2/T5/T6.

Contrato a exportar por T1:

- `PriceMode = "REFERENCE" | "CONSULT"`.
- `PriceEffect = { kind: "NONE" } | { kind: "ADD"; amount: string } | { kind: "CONSULT" }`.
- `ProductConfiguration = { formatVersion: 1; included: string; leadTimeCondition: string; fields: ConfigurationField[] }`.
- `ConfigurationField`: base `{ id: string; label: string; help: string; required: boolean }` + união `{ type: "SHORT_TEXT" | "LONG_TEXT"; maxLength: number; effect: PriceEffect }` ou `{ type: "SINGLE_CHOICE"; options: { id: string; label: string; effect: PriceEffect; imageId: string | null }[] }`.
- `ConfigurationAnswer = { fieldId: string; value: string }`; value é texto ou ID de opção, conforme definição. IDs: 1–100 caracteres alfanuméricos/hífen/sublinhado, únicos no escopo do produto; schemas estritos.
- `ConfiguredPrice = { kind: "REFERENCE"; unit: string; subtotal: string } | { kind: "CONSULT"; unit: null; subtotal: null }`.
- `validateAnswers(definition: ProductConfiguration, raw: unknown): ConfigurationAnswer[]` valida obrigatoriedade, IDs e limites e devolve respostas normalizadas ordenadas.
- `configuredPrice(input: { mode: PriceMode; basePrice: string | null; configuration: ProductConfiguration; answers: ConfigurationAnswer[]; quantity: number }): ConfiguredPrice`. Rejeita respostas inválidas; modo CONSULT não precisa de preço base.

Persistência T2: `Product.publicPriceMode String @default("REFERENCE")`, `commercialRevision Int @default(1)`, `configuration Json @default("{}")`. Configuração vazia é interpretada como definição padrão. Modo fica em coluna própria para ordenar no banco sem carregar catálogo inteiro. Validar enum no domínio e CHECK SQL; revisão positiva. JSON não duplica modo/revisão.

DTO público: `price: string | null`, `publicPriceMode`, `commercialRevision`, `configuration`, além dos campos atuais. DTO administrativo redefine `price: string` por Omit para preservar preço interno. Nunca usar spread do registro do banco na resposta pública.

Contrato T3: `InquiryItem` passa a incluir `lineId: string`, `answers: ConfigurationAnswer[]`, `commercialRevision: number | null`, `seenPrice: ConfiguredPrice | null`, `answerLabels: { fieldId: string; label: string; valueLabel: string }[]`, além de produto/cor/tamanho/quantidade. Rótulos de recuperação respeitam limites equivalentes aos campos (valor textual até 500) e nunca validam resposta. `InquiryEnvelope = { formatVersion: 2; items: InquiryItem[] }`.

Contrato T4: preservar nomes de `InquiryReview` e `reviewInquiry(raw: unknown): Promise<InquiryReview>`. Cada linha retorna lineId, respostas/rótulos canônicos, revisão atual, preço discriminado, problemas por campo e `requiresConfirmation: boolean`. Resumo retorna `knownTotal: string | null`, `consultCount: number`, `ready: boolean`, `message`, `contact`, `channel`, `copyRequired: boolean`. `ready` exige linhas válidas e revisões confirmadas; CONSULT válido não bloqueia. Confirmação atualiza revisão/preço vistos na lista e força nova conferência antes do contato. Essa confirmação é UX, nunca autoridade de preço.
