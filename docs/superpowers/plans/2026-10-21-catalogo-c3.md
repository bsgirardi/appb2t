# C3 — Quantidades, kits e montador 2D: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Oferecer faixas individuais e montagem de kits com desconto próprio, preservando composição e condições recebidas até orçamento, impressão e conversão existente.

**Architecture:** Evolução integrada de C1/C2: funções puras de preço/contexto, cadastro relacional de kits, seleção versionada e snapshots imutáveis. O montador compartilha o configurador e a lista; o servidor determina elegibilidade, preços e origem. Cada tarefa tem verificação própria, mas a entrega pública depende do fluxo completo.

**Tech Stack:** Next.js 16.3.8, React 19.3, TypeScript, Prisma 6.19, PostgreSQL, Zod 4, decimal.js, Vitest e componentes existentes; sem nova dependência de arraste.

**Spec:** [Especificação aprovada](../specs/2026-10-21-catalogo-c3-design.md), commit `396742a`, aprovada pelo usuário após sua apresentação. Base de produto: `origin/main` em `d9497ad`.

## Global Constraints

- Manter até 20 linhas comerciais no total da lista e até 99 unidades por combinação/contexto.
- Até dez faixas individuais por produto, mínimos distintos de 1 a 99; base unitária positiva; adicionais depois da faixa.
- Até 20 instâncias não vazias de kit, 50 produtos permitidos por definição e dez faixas por kit; mínimos de 1 a 1.980.
- Todas as unidades contam, inclusive componentes repetidos; não contar somente produtos diferentes.
- Desconto do kit não acumula com faixas individuais dos produtos.
- Percentual maior que zero e menor que 100%, até duas casas; valor fixo positivo abatido uma única vez por instância.
- Usar Decimal e arredondamento HALF_UP. Limite monetário `9999999999999999.99`; rejeitar desconto igual ou superior à base.
- Qualquer componente sob consulta mantém subtotal completo, desconto aplicado e líquido do kit nulos; nenhuma aplicação parcial.
- Histórico recebido e cálculo de preparação imutáveis; edição posterior usa valores negociados e revisão explícita do desconto.
- Manter limite público de 256 KiB em streaming; orçamento autenticado até 16 MiB e 100 linhas.
- Conferir 320/390/1440 px, claro/escuro e preferência de movimento reduzido no navegador integrado. Alvos de pelo menos 44 px.
- Sem kits aninhados, preço fechado, uploads do visitante, aprovação de arte, checkout, cobrança, reserva ou nova automação de estoque/produção.
- Antes de qualquer código Next, ler os guias pertinentes em `node_modules/next/dist/docs/`, conforme AGENTS.md. Não alterar dependências para contornar APIs antigas.
- Trabalhar isoladamente; preservar checkout original, dados e serviço C2. Bancos de testes mutáveis devem ser locais, descartáveis, nomeados `b2t_test`.

## Review Focus

1. Duas abas editam a mesma montagem durante uma tentativa pendente: preservar tentativa e alterações posteriores, inclusive posições (tarefas 6 e 7).
2. Nome visualmente igual em Unicode e IDs legados colidentes: normalização comercial consistente, contextos separados e recuperação sem perda (tarefas 1 e 6).
3. Produto ou permissão muda durante revisão/envio, com pool de uma conexão: snapshot coerente, sem deadlock ou outra conexão (tarefas 3 e 4).
4. Maior seleção válida produz snapshot maior que o corpo público: impor limite explícito e roundtrip completo no editor, sem truncamento (tarefas 4 e 8).
5. Operador duplica/exclui linha e depois converte orçamento: origem nunca migra para outra linha e desconto não é reaplicado (tarefa 9).

## Organização e contratos entre tarefas

Novos módulos de domínio ficam em `src/domain/kits/`: `types.ts` (contratos), `validation.ts` (definição), `pricing.ts` (cálculo), `selection.ts` (grupos), `composition.ts` (geometria), `draft.ts` (recuperação) e `document.ts` (histórico/revisão). `src/domain/products/quantity-pricing.ts` cuida apenas das faixas individuais. Reutilizar `ConfiguredPrice`, `InquiryItem`, normalização de respostas e limites monetários existentes.

Tipos públicos novos, definidos antes de consumidores:

```ts
type QuantityTier = { minQuantity: number; baseUnitPrice: string };
type KitDiscountTier = { minQuantity: number } & (
  { kind: "PERCENT"; percent: string } | { kind: "FIXED"; amount: string }
);
type KitPlacement = { lineId: string; x: number; y: number; z: number };
type KitGroupInput = {
  instanceId: string;
  kitId: string;
  commercialRevision: number | null;
  placements: KitPlacement[];
  seenPrice: KitPrice | null;
};
type KitPrice = {
  kind: "REFERENCE" | "CONSULT";
  quantity: number;
  knownSubtotal: string;
  subtotal: string | null;
  discount: string | null;
  total: string | null;
  tier: KitDiscountTier | null;
};
type KitSelection = {
  schemaVersion: 2;
  items: InquiryItem[];
  groups: KitGroupInput[];
};
```

`InquiryItem` recebe `kitInstanceId?: string`; ausência significa avulso. `KitDefinitionInput` contém nome, descrição, publicação, posição, produtos permitidos e faixas; `KitDTO` adiciona id, version e commercialRevision. `KitGroupSnapshot` inclui schemaVersion 1, identidade, nome, revisões, tabela completa recebida, associação por lineId, imagens referenciadas, posições e `KitPrice`. `CatalogKitDocument` contém schemaVersion 1, grupos recebidos e cálculo de preparação. Não duplicar grupo em cada linha.

Seleção interna nova usa schemaVersion 2; envelope local usa formatVersion 3 e revision opaca para conflitos. C2 v1 continua aceito sem grupos, convertido para seleção vazia de grupos. Versões desconhecidas são rejeitadas explicitamente. Money é string decimal com duas casas nas saídas; nenhum cálculo por float.
